# Colorado Avalanche Risk Research Prototype

**Research prototype only. NOT for real safety decisions.** Outputs are not forecasts, official CAIC danger ratings, or guidance for travel decisions. Avalanche observations are incomplete and the negative examples in this project are *unreported point-days*, not verified non-avalanche days.

Python 3.10+. From this directory, create an environment and install `requirements.txt`. Configuration is in `config.py`. The current settings use `START_SEASON = 2010`, `END_SEASON = 2025`, and all ten listed Colorado backcountry zones, covering Nov 1, 2010 through May 31, 2026. `DATA_START_DATE` and `DATA_END_DATE` are unset, so dataset building uses the winter-season bounds. `NEGATIVE_RATIO`, paths, request limits, and User-Agent are also in `config.py`.

## Verified data sources and schemas

1. **Labels — CAIC.** The Avalanche Table page has a human-operated **Download CSV** control. Its frontend calls `GET https://lb-octonaut.avalanche.dev/api/v2/avalanche_observations`; the inspected live response is a JSON array with pagination headers (`page-items`, `total-pages`, `total-count`) and `id`, `observed_at`, `date_known`, `latitude`, `longitude`, nested `backcountry_zone.title`, `aspect`, `angle_average`, `start_zone_elevation`, `destructive_size`, `primary_trigger`, `number`, and nested `avalanche_detail.description` fields. The table code also maps `type_code`, `secondary_trigger`, `relative_size`, and `comments`. A live page-size request with `per=1000` returned 1,000 records and 29 total pages. Date certainty values sampled were `Known` and `Estimated`; `Known` is treated as exact, and Estimated dates are excluded. The response has no structured caught/buried counts, so those remain missing. Aspect is an 8-point compass code, elevation can be a treeline code while start-zone elevation is feet, size is a D-scale code, and triggers are codes.

   CAIC’s [Terms of Use](https://avalanche.state.co.us/terms-use) explicitly prohibit use of computerized robots or data mining of information presented on the website. For that reason this project does **not** automate requests to the CAIC endpoint. Download the CSV through the page manually and place it at `data/raw/caic/avalanche_observations.csv` (or use the download file in the project root). `collect_caic.py` accepts the page's observed display headers, including `Observation ID`, `Date`, `Date Known`, `Longitude`, `latitude`, `Destructive Size`, `Area`, `Aspect`, `Trigger`, and `Type`. It maps fields the export actually supplies; elevation and slope are left missing because the table exports a treeline band rather than numeric elevation and no slope angle. Caught/buried counts are also left missing. A normalized CSV may instead use these columns:

   `event_id,date,date_certainty,latitude,longitude,forecast_zone,elevation_m,aspect,slope_angle,size_raw,trigger_type,caught,buried`

   `date_certainty` can be `exact`, `known`, or `within_1_day`; coordinates are decimal WGS84; `size_raw` accepts half sizes such as 2.5. `event_id` should be stable across slides; the page's `Observation ID` is a report ID and may repeat for distinct slide rows, so the converter incorporates coordinates. `Date Known=Known` maps to exact; `Estimated` is dropped because its uncertainty interval is unspecified. Aspect is converted to degrees. The page CSV's `Elevation` field is a treeline band, not numeric elevation, and does not contain slope angle; those values are left missing. The public coordinates may be shifted for privacy; the converter keeps a location-quality flag. Rows without coordinates and dates outside the exact/±1 day certainty set are discarded. The converter does not infer caught/buried counts from descriptions.

2. **SNOTEL — NRCS AWDB REST.** Verified base URL `https://wcc.sc.egov.usda.gov/awdbRestApi`, OpenAPI `https://wcc.sc.egov.usda.gov/awdbRestApi/v3/api-docs`. Station inventory is `GET /services/v1/stations` (station triplets such as `*:CO:SNTL`, `elements`, `durations`, `returnStationElements`, `activeOnly`). Daily data is `GET /services/v1/data` (`stationTriplets`, `elements`, `duration=DAILY`, `beginDate`, `endDate`, optional flag options). OpenAPI response is an array of `StationDataDTO`; each station data object contains station metadata and data series; each series has `stationElement` and `values`, whose daily records contain `date` and `value` (flags optional). WTEQ (snow water equivalent) and PREC are requested. The checked-in collector expects station identity plus `data[].stationElement.elementCode` and `data[].values[].date/value`; compare the live response with the OpenAPI schema if AWDB changes. Respect the API's request-size constraints by splitting requests; current collector caches each station-season request and backs off on errors.

3. **Weather — Open-Meteo Historical Weather API.** Verified endpoint `GET https://archive-api.open-meteo.com/v1/archive`. Request uses `latitude`, `longitude`, `start_date`, `end_date`, `daily`, `timezone`, and model `era5_land`. The daily response contains a `time` array, one array per requested daily variable, and `daily_units`. Data is modeled reanalysis, not a point observation; grid resolution is coarse relative to avalanche terrain. Daily variables include snowfall, precipitation, temperature, and wind.

4. **Terrain — USGS The National Map / 3DEP.** Verified point endpoint `GET https://epqs.nationalmap.gov/v1/json` with `x` longitude, `y` latitude, `wkid=4326`, `units=Meters`, `output=json`; response nests elevation under `USGS_Elevation_Point_Query_Service.Elevation_Query.Elevation`. This endpoint supplies elevation only. Slope and aspect are retained from the CAIC label file; this prototype does **not** derive them from a DEM raster. A real DEM-based slope/aspect workflow remains future work.

## Run order

1. Download the CAIC CSV through the page in a human browser session and save it at `data/raw/caic/avalanche_observations.csv` or the project root's downloaded filename.
2. `python -m src.collect_caic --help`, then `python -m src.collect_caic` to normalize either the CAIC table export or a CSV in the normalized schema to Parquet.
3. `python -m src.collect_terrain` and `python -m src.collect_weather`; `python -m src.collect_snotel` downloads daily CO SNOTEL measurements. Each request is cached under `data/raw/*/cache`; existing responses are skipped. Requests use a descriptive User-Agent, a delay and exponential retries.
4. `python -m src.build_dataset` joins sources and samples pseudo-absence days at event coordinates.
5. `python train_model.py` saves `models/hurdle_model.joblib` (occurrence probability and conditional size model).
6. Prepare a one-row CSV with the feature fields and run `python predict.py --input path/to/row.csv`. Output includes P(avalanche), expected D-size conditional on an avalanche, probability-times-size risk score, and category. It always includes the research-only notice.

### Local interactive UI

From this directory, run `python ui.py --help` for options, then `python ui.py` and open `http://127.0.0.1:8765`. The UI uses the saved hurdle model and accepts a date and aspect in degrees. Its mountain is an illustrative SVG that animates after prediction; it is not derived from real terrain or a physical snow model. The current fitted model only uses date and aspect, so the UI intentionally does not imply that slope angle, elevation, weather, or snowpack influence its output. The page and every prediction are labeled as research-only and not for safety decisions. Keep the server bound to localhost unless you deliberately configure otherwise.

The current build uses the supplied full-range CSV and winter bounds. It produced 3,940 exact-date positive rows and 19,700 sampled pseudo-absence rows. No weather, SNOTEL, or terrain data were collected for this run, so the saved model uses only calendar and aspect features. The report's occurrence ROC AUC is from a random row split; it is not a temporal or spatially independent validation. Existing API caches are retained; API collectors skip downloaded request files.

## Known limitations

- CAIC reports are incomplete, location privacy may shift coordinates, the table export has no numeric slope/elevation or caught/buried counts, and availability of a complete historical export is unverified. CAIC prohibits automated scraping, so labels require a human-downloaded CSV. The current file has 28,607 rows dated November 2010 through May 2026. Only 4,226 rows are marked `Known` and fall in winter dates; 3,976 of those have a valid D-size before deduplication. The remaining rows are mostly `Estimated`, which the normalizer excludes because their date uncertainty is unspecified.
- An unreported event is not evidence that no avalanche occurred. The current negative sampling creates weak pseudo-absences and the fitted probability is not calibrated to the true avalanche base rate.
- Terrain coverage is point-based and does not derive slope/aspect from DEMs; the requested slope/day prediction is only as useful as the supplied slope values.
- SNOTEL station values are currently aggregated by date across stations in dataset building, a crude proxy that ignores spatial distance. Open-Meteo reanalysis is also coarse for steep terrain.
- The current model uses about 3,940 positive rows and sampled pseudo-absences derived from only avalanche-report locations. These are not verified negatives. It has no measured weather, snowpack, slope, or numeric elevation features. Current occurrence ROC AUC is about 0.68 on a random row split; conditional-size MAE is measured on training rows. These metrics do not establish temporal/spatial generalization or probability calibration.
- Risk category bands are prototype thresholds on probability × expected D-size: `<0.5` Low, `<1.0` Moderate, `<1.5` Considerable, `<2.5` High, and otherwise Extreme. They are not CAIC danger ratings.
- Size modeling needs sufficient known D-scale labels. `size_d` is half-step rounded from the original size in normalization.
